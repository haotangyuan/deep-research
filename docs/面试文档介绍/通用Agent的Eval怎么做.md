# 通用 Agent 的 Eval 怎么做

## 1. 总起：核心思想和方法

通用 Agent 的评测对象不是模型的一次静态回答，而是一次完整的任务执行过程（episode）。

在一次 episode 中，Agent 会接收用户目标，在特定环境中进行规划、调用工具、观察工具返回结果、修正策略，最后交付结果或改变环境状态。因此，Agent Eval 不能只检查最终回答“看起来是否正确”，还要评价：

- Agent 是否真正完成了用户目标；
- 最终环境状态是否正确；
- 执行过程是否安全、合理且可控；
- 多次执行是否稳定；
- 使用了多少时间、Token、工具调用和费用；
- 是否给用户带来了额外的确认、返工和接管负担。

Agent Eval 的核心思想可以概括为：

> 给 Agent 一个真实任务和可复现的执行环境，让它自主完成任务；再由 Agent 无法控制的外部 Grader，根据隐藏验收条件判断任务是否成功。

### 1.1 四个核心原则

#### 外部验证优先

不能根据 Agent 自己声称“已经完成”来评分，而应该检查真实环境状态、测试结果、数据库记录、生成文件或最终产物。

例如，评测“取消订单 Agent”时，不能只检查最终回复中是否包含“订单已经取消”，还需要验证：

- 订单状态是否真的变成 `cancelled`；
- 退款金额是否正确；
- 是否没有修改其他订单；
- 是否产生了不应该发生的副作用。

#### 结果与过程并重

最终结果正确，不代表执行过程安全；执行过程看起来合理，也不能替代最终结果验证。

例如：

- Agent 最终完成了任务，但过程中泄露了敏感信息，不能视为安全成功；
- Agent 的规划过程看起来合理，但最终数据库状态错误，不能视为任务完成；
- Agent 误删文件后又恢复，最终状态虽然正确，但仍需要在轨迹评测中记录风险行为。

#### 多维度而非单一分数

Agent 的质量不能只由一个成功率表示。通常需要同时考察：

- 结果正确性；
- 可靠性；
- 执行过程质量；
- 安全性；
- 效率；
- 用户体验。

#### 离线与线上形成闭环

离线 Eval 用于在固定环境中稳定地比较不同模型或 Agent 版本；线上 Eval 用于验证 Agent 在真实用户和真实任务分布中的价值。

两者应该形成持续闭环：

```text
线上失败案例
    ↓
匿名化并加入 Eval 任务集
    ↓
修复模型、Prompt、Agent Loop 或工具
    ↓
运行完整离线回归
    ↓
小流量上线验证
    ↓
继续收集新的失败案例
```

### 1.2 Agent Eval 的基本流程

一次完整的 Agent Eval 通常包含以下步骤：

1. 定义用户、任务边界和成功状态；
2. 构造真实、分层且尽量没有数据泄漏的任务集；
3. 固定执行环境、工具、权限和资源预算；
4. 运行完整 episode，并保存执行轨迹；
5. 使用确定性 Grader、规则、LLM Judge 和人工评审组合评分；
6. 进行多次运行、统计比较和回归检查；
7. 对失败案例进行分类和根因分析；
8. 通过 Shadow、Canary 和线上指标验证真实价值。

### 1.3 Agent Eval 的主要评价维度

| 维度 | 核心问题 | 常见指标 |
|---|---|---|
| 结果正确性 | 任务最终是否真正完成？ | 任务成功率、测试通过率、状态校验 |
| 可靠性 | 重复运行是否稳定？ | pass@1、方差、置信区间 |
| 过程质量 | Agent 是否采取了合理且可控的路径？ | 无效循环、错误恢复、验证行为 |
| 安全性 | 是否越权、泄露或产生不可逆副作用？ | 违规率、审批遵守率、事故率 |
| 效率 | 完成任务消耗了多少资源？ | 耗时、Token、工具调用次数、成本 |
| 用户体验 | 用户需要介入多少？ | 接管率、返工率、澄清次数 |

## 2. 分点介绍：完整的 Agent Eval 体系

### 2.1 定义任务与成功条件

设计 Eval 时，首先要回答三个问题：

1. Agent 服务谁？
2. Agent 需要完成什么任务？
3. 任务完成后，环境应该处于什么状态？

一个完整的任务定义通常包括：

```yaml
task:
  initial_state: 执行前的环境快照
  user_request: Agent 接收到的自然语言任务
  available_tools: Agent 可以调用的工具
  constraints: 时间、Token、费用和权限限制
  hidden_success_criteria: Agent 看不到的验收标准
```

成功条件应该尽量落到可验证的环境状态，而不是停留在“回答看起来不错”。

需要明确：

- 初始状态：文件、网页、数据库、账号和已有上下文；
- 用户可见目标：Agent 实际接收到的任务描述；
- 隐藏验收条件：Grader 用来判断成败的标准；
- 操作约束：允许使用的工具、时间、Token、费用和权限。

### 2.2 构造任务集

任务集既要覆盖真实使用分布，也要主动暴露 Agent 的能力边界。

常见任务来源包括：

- 匿名化的真实生产任务；
- 人工设计的核心能力任务；
- 边界和异常任务；
- 历史失败案例和线上事故；
- 安全和对抗任务；
- 公开 Benchmark；
- 私有 Holdout 任务集。

任务应该按照以下维度分层：

- 业务领域；
- 用户群体；
- 任务难度；
- 任务长度；
- 工具类型；
- 风险等级；
- 是否涉及环境状态修改；
- 是否需要长期规划和错误恢复。

不能只看总体平均成功率。某个版本总体提升，并不代表所有任务类型和用户群体都提升。局部回归可能被平均值掩盖。

### 2.3 建立可复现的执行环境

Agent 的表现高度依赖环境，因此比较不同版本时需要尽量固定：

- 模型版本；
- 系统提示词；
- Agent Harness 版本；
- 文件系统和代码仓库快照；
- 数据库内容；
- 浏览器状态；
- 工具接口和依赖版本；
- 网络条件；
- 权限配置；
- Token、步骤数、时间和费用预算；
- 重试策略；
- 并发策略；
- 随机种子和当前时间。

如果环境不可复现，就很难判断分数变化来自：

- 模型能力变化；
- Prompt 变化；
- Agent Loop 变化；
- 工具接口变化；
- 环境漂移；
- Grader 变化。

### 2.4 记录完整执行轨迹

一次 episode 至少应该记录：

- 每一步模型决策和可见上下文；
- 工具名称、调用参数和返回结果；
- 工具错误和重试行为；
- 文件、网页、数据库或外部系统的状态变化；
- 最终回答；
- 最终生成的产物；
- Agent 提供的验证证据；
- Token、耗时、费用和步骤数；
- 用户确认和人工接管点。

完整轨迹既用于评价过程质量，也用于失败分析和问题定位。

### 2.5 设计 Grader

Grader 应优先使用客观、可重复的验证方式。一般优先级为：

```text
环境最终状态验证
    ↓
确定性测试
    ↓
结构化规则
    ↓
LLM Judge
    ↓
人工评审
```

#### 确定性 Grader

适用于可以程序化验证的任务：

- 单元测试、集成测试；
- 数据库状态查询；
- 文件是否生成；
- 数值是否正确；
- JSON Schema 是否满足；
- 页面是否成功部署；
- 邮件是否发送给正确的收件人。

#### 规则 Grader

适用于结构和约束检查：

- 输出格式是否正确；
- 是否包含必需字段；
- 是否遵守权限要求；
- 是否提供有效引用；
- 是否修改了禁止修改的文件；
- 是否在高风险操作前请求确认。

#### LLM Judge

适用于难以完全程序化的主观维度：

- 报告是否完整；
- 是否回答了用户问题；
- 解释是否清晰；
- UI 是否符合设计目标；
- 研究是否覆盖了关键方面。

使用 LLM Judge 时，需要注意：

- 提供清晰、可操作的 Rubric；
- 使用人工标注集进行校准；
- 监控 Judge 与人工判断的一致率；
- 随机交换候选答案顺序；
- 隐藏被评测模型的身份；
- 对争议结果进行人工复核；
- 防止被评测 Agent 通过输出内容攻击 Judge。

#### 人工评审

适用于：

- 高价值任务；
- 主观性较强的任务；
- 安全风险较高的任务；
- 自动 Grader 无法可靠覆盖的情况。

### 2.6 Outcome Eval 与 Trajectory Eval

Agent Eval 可以分为两类：

#### Outcome Eval

判断最终目标是否达成：

- 最终状态是否正确；
- 测试是否通过；
- 用户要求的产物是否生成；
- 是否存在功能回归。

#### Trajectory Eval

判断 Agent 是如何完成任务的：

- 是否出现无效循环；
- 是否选择了错误工具；
- 是否正确处理工具失败；
- 是否读取了不必要的敏感信息；
- 是否执行过危险操作；
- 是否在需要时请求用户批准；
- 是否在没有验证结果时声称成功。

轨迹评测不应该强迫 Agent 模仿唯一的参考路径。不同路径都可能正确，轨迹评测应该重点约束：

- 安全性；
- 验证行为；
- 明显错误；
- 明显低效；
- 不必要的副作用。

### 2.7 鲁棒性与安全评测

同一个任务应该构造不同扰动和对抗变体，例如：

- 改写用户措辞；
- 移动文件位置；
- 加入无关信息；
- 模拟工具调用失败；
- 模拟网络异常；
- 提供不完整或互相冲突的信息；
- 改变时间、预算和可用工具；
- 改变 Agent 权限；
- 在网页、邮件、文档或仓库中加入 Prompt Injection；
- 测试隐私泄露和越权操作；
- 测试不可逆操作；
- 测试用户中止后 Agent 是否立即停止。

安全不能只依赖模型拒绝，还需要系统层面的保护：

- 最小权限；
- Sandbox；
- 高风险操作审批；
- Allowlist；
- 审计日志；
- 可回滚设计；
- 敏感信息隔离。

### 2.8 统计分析与版本比较

Agent 输出具有随机性，同一个任务运行多次可能产生不同结果。因此不能只运行一次，也不能只挑选表现最好的一次。

常见指标包括：

- `pass@1`：第一次运行成功的概率；
- `pass@k`：运行 k 次后至少成功一次的概率；
- 平均成功率；
- 运行方差；
- 置信区间；
- 成功任务的平均成本；
- 成功任务的平均耗时；
- 每单位成本带来的成功率。

版本比较时应该：

- 让新旧版本运行相同任务；
- 使用相同环境、权限和预算；
- 使用配对实验；
- 计算置信区间或使用 Bootstrap；
- 按任务类型、风险等级和用户群体分层；
- 检查局部回归；
- 同时报告成功率、成本和延迟。

例如：

```text
Agent A：成功率 72%，平均成本 $0.20
Agent B：成功率 75%，平均成本 $1.80
```

不能直接认为 Agent B 更好，需要结合业务对成功率、成本和延迟的要求进行判断。

### 2.9 Failure Analysis

失败不一定意味着模型能力不足。建议建立统一的失败分类。

#### 感知失败

Agent 没有发现完成任务所需的信息。

#### 规划失败

Agent 缺少关键步骤，或者选择了错误策略。

#### 工具失败

Agent 选择了错误工具、传入了错误参数，或者工具接口本身出现问题。

#### 状态跟踪失败

Agent 忘记已有信息，或者错误判断了当前环境状态。

#### 恢复失败

Agent 遇到工具错误或执行失败后，无法调整方案。

#### 验证失败

Agent 没有检查真实结果，却错误地声称任务已经成功。

#### 安全失败

Agent 发生越权、信息泄露或危险副作用。

#### 评测失败

任务描述、执行环境或 Grader 本身存在缺陷。

进行根因分析时，可以按照下面的层级逐层排查：

```text
模型
  ↓
Prompt
  ↓
Agent Loop
  ↓
工具接口
  ↓
执行环境
  ↓
Grader
```

### 2.10 Offline Eval 与 Online Eval

离线评测负责稳定、低风险地比较不同版本；线上评测负责验证真实用户价值。

一个常见的上线流程是：

1. **离线回归**：运行核心、边界、安全和历史失败任务；
2. **内部测试**：由员工或专家在真实工作流中使用；
3. **Shadow Mode**：观察 Agent 建议，但不真正执行高风险操作；
4. **Canary**：向少量用户逐步放量；
5. **A/B 测试**：比较任务成功、接管、返工、延迟和成本；
6. **失败回流**：将新的失败案例匿名化后加入 Eval 任务集。

线上指标可以包括：

- 用户接受率；
- 人工接管率；
- 返工率；
- 撤销率；
- 错误成功声明率；
- 任务完成时间；
- 用户满意度；
- 安全事故率；
- 平均成本。

### 2.11 Eval 本身也需要被评估

任务失败可能来自 Agent，也可能来自 Eval 本身：

- Prompt 缺少完成任务所需的信息；
- 隐藏测试要求了 Prompt 中没有说明的行为；
- 测试强制某种具体实现；
- 测试覆盖率不足；
- 正确实现被误判；
- 错误实现可以侥幸通过；
- 执行环境已经损坏；
- LLM Judge 与人类判断不一致。

因此，需要定期审计：

- 任务描述；
- 隐藏测试；
- 执行环境；
- Grader；
- Agent 失败轨迹；
- Grader 与人工判断的一致性。

## 3. 总结：如果让我设计一个 Agent Eval，需要考虑什么？

如果在面试或系统设计中被要求设计 Agent Eval，可以依次回答下面十个问题。

### 3.1 User & Task

- Agent 服务谁？
- 需要完成什么任务？
- 任务边界是什么？

### 3.2 Success

- 什么可观察状态代表任务真正完成？
- 是否存在隐藏验收条件？
- 如何检查副作用和功能回归？

### 3.3 Dataset

- 任务从哪里来？
- 如何覆盖真实用户分布？
- 如何按领域、难度和风险分层？
- 如何防止训练数据和评测数据泄漏？
- 是否有私有 Holdout？

### 3.4 Environment

- 如何固定模型、Prompt 和 Agent Harness？
- 如何固定工具、依赖、网络和环境快照？
- 如何限制时间、Token、步骤数、费用和权限？

### 3.5 Trace

- 需要保存哪些模型输出和工具调用？
- 如何记录环境状态变化？
- 如何记录错误、重试和用户介入？
- 如何发现隐藏副作用？

### 3.6 Grader

- 哪些结果可以确定性验证？
- 哪些结果需要规则 Grader？
- 哪些主观部分需要 LLM Judge？
- 如何用人工标注校准 LLM Judge？
- 如何防止 Judge 被 Agent 输出攻击？

### 3.7 Metrics

- 是否关注 `pass@1`？
- 如何衡量稳定性和方差？
- 如何衡量安全性？
- 如何衡量成本和延迟？
- 如何衡量用户接管和返工？

### 3.8 Robustness

- 工具失败时 Agent 能否恢复？
- 用户措辞变化后是否仍能完成？
- 信息缺失或冲突时如何处理？
- 是否能抵抗 Prompt Injection？
- 是否遵守权限和审批边界？

### 3.9 Analysis

- 新旧版本是否运行相同任务？
- 是否进行了多次运行和配对比较？
- 提升是否具有统计显著性？
- 是否检查了局部任务和高风险场景的回归？
- 失败发生在模型、Prompt、Agent Loop、工具、环境还是 Grader？

### 3.10 Online

- 如何进行 Shadow Mode？
- 如何小流量 Canary？
- 上线时观察哪些指标？
- 发生回归时如何停止和回滚？
- 如何把线上失败回流到离线任务集？

### 3.11 建议的发布门槛

- 安全指标不得显著退化；
- 核心任务的 `pass@1` 不得退化；
- 高价值任务应有统计显著提升；
- 历史失败和事故回归集必须通过；
- 成本与延迟增长必须与用户价值提升相匹配；
- 局部人群或高风险场景的退化不能被总体平均值掩盖。

### 3.12 面试中的精简回答模板

> 我会先明确用户任务和可验证的成功状态，再从真实流量、历史失败和对抗场景中构造分层任务集。评测时固定模型、环境、工具、权限和资源预算，运行完整 episode 并记录执行轨迹。评分优先使用环境状态和确定性测试，主观部分再使用经过人工校准的 LLM Judge。最后通过多次运行、配对实验、置信区间、分层回归和失败归因判断版本是否真正提升，并通过 Shadow、Canary 和线上反馈闭环验证真实用户价值。

### 3.13 常见误区

- 只看公开 Benchmark，不建立私有真实任务集；
- 只看最终回答，不验证环境状态和副作用；
- 让被评测 Agent 自己决定是否成功；
- 让未经校准的 LLM Judge 决定最终分数；
- 只运行一次，忽略随机性和置信区间；
- 只看总体平均分，忽略局部回归；
- 把所有失败归因于模型，忽略工具、环境和 Grader 缺陷；
- 只优化成功率，忽略安全、成本、延迟和用户介入。

## 结语

成熟的 Agent Eval 不是一个分数，而是一套持续运转的测量系统。

它将真实任务、可复现环境、外部 Grader、执行轨迹、统计分析和线上反馈连接起来，最终回答两个核心问题：

1. Agent 是否真正完成了用户目标？
2. Agent 是否以稳定、安全、经济且可控的方式完成了任务？
